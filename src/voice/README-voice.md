# Voice turn lifecycle (src/voice)

1. Browser mic frames (Int16 PCM 16 kHz, binary WS) are forwarded as-is to one Deepgram `listen` socket per connection (`deepgram.ts`), opened on the model of the session language: `nova-3` for English, `nova-2` with `language=tr` for Turkish (nova-3 does not list Turkish); endpointing, interim results, VAD events and smart format are the same on both (`deepgramListenUrl(lang)`). The socket is opened on the first mic frame, not at page load (an idle tab holds no Deepgram slot); frames that arrive while it is still connecting are buffered (up to 2 s) and flushed on open. If Deepgram closes the socket it is reopened on the next frame with a 500 / 1500 / 4000 ms backoff; after three failures voice input stays off for a minute and the client gets one error event. A `KeepAlive` JSON goes out every 8 s so silence never kills an open socket.
2. Deepgram interim results are relayed as `{type:"stt", final:false}`; `is_final` pieces are accumulated, and the utterance becomes a user turn on `speech_final:true` or on `UtteranceEnd` after finals. `{type:"text"}` from the client is the same turn path without STT; its `source` is `text`, a spoken one is `voice`.
3. `t0` is taken in `session-voice.ts` at the instant that final is processed (or the text message is parsed). `sttFinalMs` is measured backwards from `t0` to the estimated wall time the user stopped speaking. Deepgram stamps words on its audio clock (seconds of audio received), we know how much audio we sent (`bytesSent / 32` ms) and when the last frame went out, so `speechEndWall = wallAtLastFrame - (audioSentMs - lastWordEndMs)`. The anchor is refreshed on every frame, so a gap in the mic stream (Stop/Start mic, tab throttling) does not inflate later values. It is 0 for text turns. Text messages longer than 2000 chars are rejected with an error event.
4. A turn gets an id (`t<seq>-<hex>`) that stamps every `agent_text`, `tool`, `latency` event and the `played` report, so late events from an old turn are attributable and droppable.
5. If a previous turn is still running (model busy or TTS draining) the new final cancels it: `supportAgent.abort()`, `TtsStream.cancel()`, `clear_audio`, and the turn is marked `cancelled`. The new turn then waits for `agent.waitForIdle()` before `sendUserText`, because Pi refuses a prompt while streaming.
6. TTS engines and fallback (`tts.ts` is the shared stream contract for the two vendor engines; each lists the languages it speaks). Per turn the engine is picked in this order among the vendor engines that speak the turn's language: ElevenLabs (`elevenlabs.ts`, English and Turkish with the same voice, `language_code=tr` on the Turkish socket) while `ELEVENLABS_API_KEY` exists and it has not failed twice in this turn; otherwise Deepgram Aura (`deepgram-tts.ts`, model `DEEPGRAM_TTS_MODEL`, default `aura-2-athena-en`, overridable per deployment with the `DEEPGRAM_TTS_MODEL` env var, English only, same `DEEPGRAM_API_KEY` as STT); otherwise the browser's own speech synthesis (last resort, item 6a below); otherwise text only, and only then. A Turkish turn therefore never opens an Aura socket: after two ElevenLabs failures it falls to the browser tier instead of going silent. At `t0` a stream is opened on the picked vendor engine so its connect cost hides behind the model's time-to-first-token (ElevenLabs is one `stream-input` socket per utterance with `inactivity_timeout=180`; the Aura socket is one `/v1/speak` socket per turn, and an idle one was still open after 150 s in the vendor check); the browser tier has no socket to pre-open, so it is only entered lazily, at the first sentence that needs it. A pre-opened vendor socket that goes away before any text was sent is treated as idle: no toast, not counted, the next sentence opens a new one. A real failure (401, 429, API error message, mid-stream drop) gets a replacement stream that re-sends the sentences the dead stream's audio cannot have covered (`lostText`, `lostChunks` in `tts.ts`): everything written when no audio at all came back; otherwise every chunk written after the latest audio frame plus any earlier chunk for which too little audio arrived at a per-engine speaking-rate floor (40 ms per character for ElevenLabs, 60 for Aura, both below the measured 47 and 70), then whatever was still queued. Engines synthesize a socket's chunks in order, so from the first chunk that fails the test everything after it counts as lost; when the estimate is wrong it repeats a sentence rather than losing one. The replacement comes from the same engine for its second stream, then from the next vendor engine, then from the browser tier, so a turn can switch from ElevenLabs to Aura to the browser mid-sentence-list; once a turn has switched to the browser tier it stays there for the rest of that turn (never mixed with vendor binary audio in one turn). A stream that stops being writable without reporting an error (the vendor sent a close frame, the TCP close has not arrived: `ws` sits in CLOSING until the FIN or its 30 s timer) is retired the moment the next sentence or the end-of-input reaches it: same failure path, lost sentences re-sent, failure counted, then the socket is terminated so nothing lingers. When every vendor engine is used up and the browser tier is also unavailable (client `caps.browserTts:false`, or chaos `browsertts`), or the loss is unrecoverable (a flushed stream whose audio covered every sentence written), TTS is off for the rest of that turn with a single error toast, while the text keeps streaming. A vendor engine that used up its two streams in one turn rests for 60 s (`TTS_ENGINE_COOLDOWN_MS`, per connection, logged when set and when lifted, cleared by a reset): the next turns pre-open the next engine directly instead of paying a connect-and-reject first.

6a. Browser tts tier (last resort, `session-voice.ts`, no `TtsStream`/`TtsEngine`, no socket at all): entered once no vendor engine can speak the turn's language or every one that can is resting or used up this turn, provided the browser has not said otherwise. The client's one-shot `{type:"caps", browserTts, voices?}` (sent right after `ready`) is stored on the VoiceSession; before it arrives the server assumes `browserTts: true`, so a turn that starts in the gap between connect and caps still gets a chance at speech instead of silence (`browserOffered()` in `session-voice.ts`; chaos `fail=browsertts` forces it off regardless of caps, for demonstrating text only on purpose — `?fail=tts,browsertts` together force a turn all the way to text only even when a browser tier exists). Per completed sentence from the chunker the server sends `{type:"speak", turnId, text, lang, seq}` (`seq` 0-based, scoped to the turn) instead of opening a socket; `public/app.js` builds a `SpeechSynthesisUtterance` and calls `speechSynthesis.speak()`, which queues and plays utterances strictly in the order `.speak()` was called, so sentences never overlap without the client needing a queue of its own. The client reports `{type:"speak_start", turnId, seq, t}` on the utterance's `onstart` — this is what stamps `firstAudioMs`, the same role `played` plays for vendor audio — and `{type:"speak_done", turnId, seq, t}` on both `onend` and `onerror`, so a failed utterance cannot hang the turn either; the server ignores the client's own `t` and stamps its own receipt time, exactly like `played`. The turn's TTS is not "done" until every `seq` it sent has a `speak_done`, or `BROWSER_SPEAK_SILENCE_MS` (10 s, `VoiceSessionOptions.browserSpeakSilenceMs` overrides it for tests) has passed since that particular `speak` with no word back, which finalizes it anyway so a lost or silent client can never hang a turn forever. `clear_audio` (barge-in, a new turn, reset) is answered client-side with `speechSynthesis.cancel()` (which empties whatever is still queued) in addition to the usual audio-buffer flush; server-side, a cancelled turn's `speak` messages simply stop going out, the same way a cancelled turn's vendor `sendText` calls stop. `ttsEngine`/`ttsEngines` report `"browser"` for these turns, in both the `latency` event and the stdout line, from the moment the first `speak_start` arrives (mirroring how a vendor engine is only credited once its first audio byte arrives). `GET /healthz` and every connection's `ready.voice.ttsEngines` list `"browser"` alongside whatever vendor engines are configured (or alone, with none): the browser tier is always structurally offered, so `features.tts` is `true` and a deployment with zero vendor keys still says so in its startup log.
7. `firstTokenMs` is stamped on the first `message_update` event whose `assistantMessageEvent.type === "text_delta"`. Each delta is sent to the client as `agent_text` and pushed through `SentenceChunker` (split on `.?!` + whitespace, or after the last comma once the buffer passes 120 chars); a `text_end` event or a tool start flushes the buffer so a pre-tool sentence is spoken before the tools run.
8. Each completed chunk goes to the engine: ElevenLabs as `{text, flush:true}` with `{audio: base64}` replies decoded to PCM; Aura as `{type:"Speak", text}` with raw PCM binary frames back (Aura synthesizes a complete sentence as soon as it arrives, first frame about 250 ms after the Speak, so no per-sentence flush is sent). `firstAudioMs` is stamped when the first PCM frame of the turn is handed to the client socket (`sendAudio`).
9. Filler, voice turns only. `tool_execution_start` starts a per-tool clock and, if the turn's source is `voice`, TTS is configured for the turn's language and nothing has been spoken yet this turn, arms a 700 ms timer. The timer is not cleared when the tool ends (in-memory tools finish in milliseconds; the silence the customer hears is the model round trip after them): it fires unless something was spoken, the model is already streaming its answer, or the turn ended, and then "One moment, let me check that." ("Bir saniye, hemen bakıyorum." in Turkish, `FILLER_TEXTS`) is synthesized once (and shown as `agent_text`). A typed turn never gets it: the customer is reading, there is no silence to fill.
10. `tool_execution_end` adds the elapsed ms to `toolMs`. Blocked-by-guard is detected structurally: blocked calls never reach `afterToolCall`, so if `session.toolLog` did not grow (or its new entry carries `blocked`) the phase is `blocked`; an executed call with `isError` is reported as `end` plus a user-facing `{type:"error"}`. The session wraps the agent's tool list (`chaos.ts`, `instrumentTools`) so an exception from a tool reaches the model as `Tool <name> failed: <message>` with the harness's `is_error` flag; the toast shows the same words. The harness feeds that result back to the model and the run continues, so the apology and the escalation offer come from the next model round (prompt territory), not from the harness stalling.
11. `agent_end` flushes the chunker remainder to TTS, sends the end-of-input (`{text:""}` to ElevenLabs, `{type:"Flush"}` to Aura), and pushes a `state` snapshot. A pre-opened stream that never received text is cancelled instead of flushed.
12. The engine answers with the remaining audio and its end marker (`isFinal:true` from ElevenLabs, `{type:"Flushed", sequence_id}` from Aura, after which the Aura socket gets `{type:"Close"}`; on the browser tier there is no socket, so "drained" means every sent `speak` has a `speak_done` or hit its safety timeout, see item 6a); only then is the turn finalized (agent idle and TTS drained, or cancelled). The `latency` event goes to the client at that moment, with `source` `voice`, `text` or `greet`, and carries `ttsEngine: "elevenlabs" | "deepgram" | "browser" | "none"`, the engine that produced the turn's first audio, i.e. the one `firstAudioMs` was measured on (a vendor engine's first PCM byte, or the browser tier's first `speak_start`; `none` when no audio was sent: text-only mode, every tier failed or was unavailable, or the turn was cut before its first frame), and `ttsEngines`, every engine credited with audio this turn in order of first frame (two entries after a mid-turn fallback, e.g. ElevenLabs then browser).
13. `playedMs` comes from the client's `{type:"played", turnId}` and is stamped with the server receipt time (client clocks are not trusted); the stdout JSON line (same fields as the event, plus `sessionId`, `lang`, `audioMs`, `chars`) is written when that report arrives or 2 s after finalization, whichever comes first, and once per turn. A report that arrives after finalization only completes the stdout line; no second `latency` event is sent, because the client tags audio with the last turn id it saw and an event for an old turn would relabel the next turn's audio.
14. Barge-in: Deepgram `SpeechStarted` while the model is busy or the client is still estimated to be playing this turn's audio (bytes sent / 32 per ms from the played or first-audio timestamp) triggers step 5's cancel path; audio chunks that arrive from the cancelled TTS stream afterwards are dropped by both the stream's `cancelled` flag and the turn's identity check. If the barge-in produces no transcript within 1.8 s (cough, click, echo leak, VAD false trigger) and interims are not still flowing, the interrupted user text is sent to the model again as a new turn (`resumedFrom` in the stdout line), at most twice per question, so the customer is never left in silence; a tool that completed during the cancelled turn (an APPLIED reschedule, say) is in the model's history and gets announced in that resumed answer. A real transcript clears the resume timer. When the answer was already fully generated and only its playback is cut, nothing is repeated (the text is on screen).
15. Client close tears everything down without reconnecting: abort the agent, cancel TTS streams and any outstanding browser-tier safety timers, `CloseStream` + close on Deepgram, flush pending latency lines. With no Deepgram or ElevenLabs key voice INPUT runs in text-only mode (mic disabled client-side, binary frames get one error event and are ignored) but voice OUTPUT still works through the browser tts tier (server logs this at startup). `server.ts` accepts `/ws` upgrades only from the page it served (Origin host equals the request Host, or an `ALLOWED_ORIGINS` entry; non-browser clients without Origin are allowed), caps WS messages at 1 MiB, reads the session language from `?lang=` on the upgrade URL, reads the ElevenLabs voice from `VOICE_ID` or `ELEVENLABS_VOICE_ID`, and reads the Aura voice from `DEEPGRAM_TTS_MODEL` (all logged at startup, alongside which source each came from). `GET /healthz` reports `features.tts` as always `true` and lists `features.ttsEngines` as the configured vendor engines plus `"browser"`, since the browser tier is always structurally offered regardless of vendor keys (a specific connection's own `ready.voice` narrows once its `caps`/chaos are known). The vendor socket URLs can be pointed at mock servers for tests (`DEEPGRAM_WS_URL`, `DEEPGRAM_SPEAK_WS_URL`, `ELEVENLABS_WS_URL`, see `vendor-url.ts`); because the API keys travel in those sockets' headers an override is honoured only for a loopback host, or for any host when `ALLOW_VENDOR_URL_OVERRIDE=1` is set explicitly. Anything else is ignored with a log line and the real vendor host is used; every override in force is listed in the startup log.

## Language (en, tr)

The `/ws` upgrade URL may carry `lang=en|tr` (default `en`, parsed in `server.ts` with `parseLang`, so `tr-TR` works too). The VoiceSession keeps it and builds its domain `Session` with it, so every tool result label, spoken summary, guard reason, the prompt, the filler and the greeting come out in that language; the `ready` event echoes it as `lang`. A `{type:"lang", lang}` client message switches it for the rest of the connection: `session.lang` changes at once (the next prompt build and tool result follow, even between the model rounds of a running turn through `prepareNextTurnWithContext`), an open Deepgram socket is dropped because one socket is bound to one model (its close is ignored: no failure count, no backoff) and the next mic frame opens a socket on the new model; the server answers with a `state` whose `session.lang` shows the new value. Speech that was in flight on the old socket is lost, so the client should switch between turns. An unknown value gets one `error` toast and changes nothing. Each turn snapshots the language when it starts (`turn.lang`), so engine choice and filler do not change halfway through an answer. `ready.voice` describes the language at connect time (`ttsEngines` lists only engines that speak it); switching to Turkish on a connection whose only engine is Aura gets one `No speech engine for tr` toast and text-only turns from then on.

Measured 2026-09-03: Deepgram nova-2 tr on a macOS `say -v Yelda` clip returned "Merhaba, en son siparişim ne durumda?" exactly (confidence 0.97, `scratch/vendor-dg-live-lang.ts`); ElevenLabs flash v2.5 with the Sarah voice and `language_code=tr` spoke the Turkish greeting (114 chars) with first audio after 424 ms and 7.2 s of speech, which Deepgram tr read back almost verbatim (`scratch/vendor-el-ws-tr.ts`).

## The assistant speaks first (greet)

`{type:"greet"}`, sent by the client once the socket is ready (and, in voice mode, once the mic is on), makes the agent open the call with a fixed line per language (`GREETINGS`: "Hi, you've reached Hemma support. I can help with an existing order. Who am I speaking with?" / "Merhaba, Hemma destek hattına ulaştınız. Mevcut bir siparişinizle ilgili yardımcı olabilirim. Kiminle görüşüyorum?"). No model call: the greeting runs through the ordinary turn machinery (`runGreeting`) so the client sees exactly what a model turn produces: a turn id, one `agent_text` delta with the whole line, the sentences through the chunker to the TTS stream that was pre-opened at `t0`, audio frames, a `state`, and a `latency` event with `source:"greet"` (`sttFinalMs` 0, `firstTokenMs` about 0, `firstAudioMs` the engine's first frame, `ttsEngine` as usual). The line is then written into the agent's history as its first assistant message (`SupportAgent.addAssistantMessage`, pi's `state.messages` setter), so the model's next answer continues the call instead of greeting again; verified with claude-haiku-4-5 in both languages (`scratch/greet-history.ts`). The greeting is honoured once per session and only before the first turn; later `greet` messages are ignored with a log line. A `reset` starts a fresh session that may be greeted again. A barge-in while the greeting plays cuts the audio (`clear_audio`) and does not re-answer: a greeting has no question to repeat (`userText` is empty, so `armResume` does nothing).

## Chaos toggles (demo only)

The `/ws` upgrade URL may carry `?fail=tool,tts,stt,browsertts` (comma separated, any subset; repeated `fail=` parameters are merged; unknown values are ignored). They are parsed in `server.ts` (`chaos.ts`, `parseChaos`), passed to the `VoiceSession`, and never read from env, so production traffic without the parameter runs with chaos off. The `ready` event reports what is active as `chaos: [...]` (`[]` by default), and a `{type:"reset"}` re-arms the one-shot failures so the demo can be replayed on one tab.

- `tool`: the first `check_resolution_options` call of the session throws `Simulated failure in check_resolution_options`; the second call works. The session wraps the tool and adds `simulateFailure: true` to that one call's params, which the domain's own `maybeFail` hook turns into the throw (src/domain is untouched). The client gets the `tool` event with `error: true` and the error toast, the model gets `Tool check_resolution_options failed: ...`, and the turn continues.
- `tts`: every ElevenLabs stream of a turn fails on the next tick without opening a socket (`FailingTtsStream`), so the retry runs, ElevenLabs is exhausted for the turn, and the sentences go through the Aura fallback when Aura speaks the turn's language (latency event `ttsEngine: "deepgram"`), or the browser tier otherwise (Turkish, or no Deepgram key; `ttsEngine: "browser"`). Two failures in the first turn also put ElevenLabs to rest for 60 s like a real outage would, so the following turns pre-open the next tier directly; a reset lifts the rest and replays the retry-then-fallback path. No ElevenLabs characters are spent on a chaos session.
- `stt`: right after the first final transcript the Deepgram listen socket is closed once (the turn it produced still runs). The client sees one error toast naming the drop; the session's reconnect backoff reopens the socket on the next audio frame after 500 ms. Audio sent during that backoff is dropped, as it would be on a real network drop.
- `browsertts`: the browser tts tier is never offered for this connection, as if every `{type:"caps"}` message had said `browserTts: false`, regardless of what the client actually reports. On its own this only changes anything once no vendor engine can speak the turn's language either (which `tts` alone does not guarantee: a healthy Aura still catches English after ElevenLabs is chaos-failed). Combined as `?fail=tts,browsertts` it forces a turn all the way to text only (`ttsEngine: "none"`, one "Speech synthesis error" or "Speech synthesis unavailable" toast depending on whether the failure happened mid-stream or was already resting) even on a deployment where the browser tier would otherwise always save the turn — the only way left to demonstrate the plain text-only path now that one exists.

## Deepgram Aura contract as verified (scratch/vendor-dg-speak.ts, 2026-09-03)

`wss://api.deepgram.com/v1/speak?model=aura-2-thalia-en&encoding=linear16&sample_rate=16000`, header `Authorization: Token <DEEPGRAM_API_KEY>`. Open took 0.7 s. First server message: `{"type":"Metadata","request_id":...,"model_name":"aura-2-thalia-en",...}`. Client messages `{type:"Speak", text}`, `{type:"Flush"}`, `{type:"Close"}` as written in the task; no divergence found. Audio comes as binary frames of raw 16 kHz Int16 PCM (1280 bytes each, no WAV header) and starts 250 ms after a `Speak` that ends a sentence, without any `Flush`; 2.1 s of audio for one sentence had arrived 2.5 s later. `Flush` produced `{"type":"Flushed","sequence_id":0}` 1.07 s after the second sentence, a second Speak + Flush on the same socket produced `sequence_id: 1` (the socket is reusable across flushes), and `Close` made the server close with 1000. `{type:"Error", description, code}` is the error shape handled by the client; `Warning` and `Cleared` are ignored. An idle socket with nothing sent stayed open for the full 150 s of `scratch/vendor-dg-speak-idle.ts`. This was verified against `aura-2-thalia-en`; the protocol is the same for every `aura-2-*` voice, only the `model` query value and `model_name` in `Metadata` change. The default voice is now `aura-2-athena-en` (`DEEPGRAM_TTS_MODEL` in `deepgram-tts.ts`, overridable with the `DEEPGRAM_TTS_MODEL` env var): "feminine, calm, smooth, professional" per Deepgram's Aura-2 catalogue, a better fit for a support line than thalia; first-audio latency measured comparable, 937 / 956 / 1125 ms over three runs with a full sentence.

A support agent you can talk to, built on Pi in one working day.

The case study asked for a small customer-support agent for an ecommerce brand, using Pi as the agent harness, with real-time voice. This page is what I built, how I decided, and how to try it. Written by Efe Demirbağ, 3 September 2026.

What it is

The product

Hemma is a fictional Scandinavian home-goods store. A customer opens the page, presses Start a call or types, in English or Turkish, and asks about an existing order. The assistant looks the order up, follows Hemma's support rules, asks for confirmation before it changes anything, and applies the change exactly once. Anything above the rules goes to a human as a case.

The three situations it handles

  • Move a delivery. Only if the order has not shipped, only to a slot the tool returned, only after a yes.
  • Damaged item. Replacement if stock exists, refund if not. Orders above EUR 200 go to a human.
  • Late delivery. VIP customers after two days, others after four. Compensation above EUR 50 goes to a human.

How I approached it as a product

The person on the phone has a problem and no patience for a menu. Good looks like: the assistant already knows their orders, names the right one, offers only real options, asks one clear question, and never does something twice. I set that as the bar before writing code, then cut everything that did not serve it: no telephony, no accounts, no database, no knowledge base. Two demo customers with four orders cover every rule in the brief.

The brief lists six tools. I kept their names and gave each a fixed job, so the model's only freedom is which tool to call and what to say. The support rules are not text for the model to remember. They are code the tools run.

Architecture

The decisions that matter

Rules are code, not prompt

Each scenario is a playbook file: which tools in which order, and a function that turns an order into the options the customer may be offered, with the EUR 200, EUR 50, two-day and four-day thresholds inside. The prompt says "offer only what the tools return". A fourth scenario is one file plus one registry line; an example is in examples/scenarios.

Confirmation and exactly once, enforced

apply_resolution is two-phase. The first call stores a proposal and returns NEEDS_CONFIRMATION. It applies only when a proposal exists and the customer's last utterance is an actual yes, checked in code with negations excluded. Every applied action is written to a ledger under a key built from order, action and parameters; a repeat returns ALREADY_APPLIED and does nothing. Pi's beforeToolCall hook is the gate, so the model cannot skip it.

Voice stays outside the agent

Speech to text and text to speech are separate layers, not a speech-to-speech model, because the guard needs the transcript text before every tool call. Interruption comes from Deepgram's speech-start event, which arrives about half a second before any transcript: the agent is aborted, the audio stream is cancelled, the browser flushes its buffer. Late audio from the cancelled turn is dropped by turn id.

Measured, not guessed

Haiku 4.5 was chosen after timing three models on the same tool turn. Every turn records four clocks: speech end, first token, first audio byte, first audio played. A scripted check replays the eight-step demo against the real model and fails the build if a tool runs out of order or an action is applied twice.

Two languages

English and Turkish, chosen for the reviewer's own market. Speech to text runs nova-3 for English and nova-2 with an explicit Turkish flag, because nova-3 has no Turkish. One ElevenLabs voice speaks both. The prompt, the dates and the confirmation wording are separate strings per language; order ids, money and product names stay the same in either.

The assistant speaks first

A fixed line per language plays before the customer says anything, no model call, written into the conversation history so the model does not greet twice. A silent page after you press Start a call reads as broken, not as waiting its turn.

Three voice tiers

ElevenLabs first, Deepgram's Aura second for English only, the browser's own speech synthesis last. The free ElevenLabs workspace ran out of characters mid-testing, and Aura has no Turkish voice at all, so the assistant needs a tier that needs no vendor key. It sounds plainer than the other two, but the call is never silent.

Trade-offs and limits

  • State is in memory per connection. Reload the page and the ledger is gone. A real deployment would put proposals and the ledger in Postgres with the same keys.
  • The yes detector is a word list with negation handling, not a model. It is deliberately dumb so it can be tested; the next step is a small classifier tool with the same interface.
  • Haiku can still ask one clarifying question in Turkish instead of acting; a tool-result hint fixed this failure mode for English. The guard makes it a wording problem, never a safety one.
  • Turkish speech recognition struggles with an English name or a spoken digit inside a Turkish sentence: a synthesized test had "Anna Weber" come back as "Nana Eber" and a customer number come back as words.
  • Browser channel, no telephony, no authentication, one ElevenLabs voice for both languages. The free ElevenLabs tier cannot use library voices through the API, so the fallback chain is real insurance, not decoration; its last tier, the browser's own speech synthesis, sounds plainer and its quality depends on which voices the operating system has installed.
  • The hosted demo runs on a free instance that sleeps after 15 minutes; the first request after that takes up to a minute.

How it was made

I wrote the contract first: layout, types, the six tool signatures, the guard rules, the WebSocket protocol, the mock data. Claude Code then wrote most of the code against that contract, in parallel per area, with an adversarial review pass per area before anything was integrated. I read every review finding, ran the real model and real voice checks myself, and I am the one who answers for what is here.
